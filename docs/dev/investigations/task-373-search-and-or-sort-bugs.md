# TASK-373: 検索AND/OR絞り込みとデフォルトソート順の不具合調査

## 症状

- 絞り込み検索でモンスタータイプを2種類選択し、AND/ORを切り替えても検索結果が変わらない（常にORのように見える）
- 通常(Normal)とチューナー(Tuner)をORで検索すると、最初に通常モンスターだけの古い順が出るままに見える

---

## 発見までの経緯（4段階）

最初に見つけた原因は主症状の説明にならず、都度「直っていない」との指摘を受けて再調査した。
最終的に**独立した2つの本物のバグ**が見つかった。

1. 拡張検索（1秒後に最大2000件まで取得するバックグラウンド処理）に検索世代を区別する仕組みがなく、
   古い検索の遅延フェッチが新しい検索結果を上書きするレースコンディション → 実在するバグだが主原因ではなかった
2. クライアント側AND/ORフィルタ（`applyClientSideFilters`）がautoモードの分岐内でしか呼ばれておらず、
   通常のname/text/pendulum検索経路では未適用だった → 症状は解消したが、これも本質的原因ではなかった
3. **`url-builder.ts` の複数パラメータ上書きバグ**（本当の原因1）
4. **`SORT_ORDER_TO_API_VALUE` のsort値の名前と実際の意味が逆**（本当の原因2、独立した別バグ）

---

## 根本原因1: url-builder.ts が複数の同名パラメータを上書きしていた

`src/utils/url-builder.ts` の `buildApiUrl()` が、呼び出し元(`buildSearchParams`)が組み立てた
`URLSearchParams`（`other=6&other=9` のような同名キーの複数パラメータを含む）を最終URLへマージする際、

```typescript
for (const [key, value] of params.entries()) {
  url.searchParams.set(key, value);
}
```

と `set()` を使っていたため、同じキーが複数回出現すると最後の値以外が全て上書きされて消えていた。

### 検証方法

Vueアプリの状態を一切経由せず、実際に生成されたリクエストURLをそのままfetchしてサーバーの
生レスポンスを直接比較する検証を行った（`applyClientSideFilters`のようなクライアント側の
後処理が結果を偽装していないかを排除するため）。

- 修正前: 融合+シンクロを選択していても、実際にサーバーへ送信されるのは `other=9`（最後の1種類）のみ
- 修正後: `other=2&other=9`（両方）が送信され、サーバー側でOR=100件・AND=0件（融合とシンクロを
  同時に持つカードは仕様上存在しないため0件が正解）と正しく分岐

### 修正

キーごとに最初の出現時だけ既存値をクリアしてから `append()` で積み増す方式に変更。
単一キーの上書き（既存仕様）は維持しつつ、複数値パラメータは全て保持されるようにした。

---

## 根本原因2: sort=20/21 の意味が名前と逆だった

url-builder.ts修正後も「通常orチューナー」の症状報告が続いた。実機で複数の現実的なシナリオ
（キーワードなし/キーワードあり・autoモード）を再現できず、一度「ブラウザのリロードが必要では」
という聞き方をしてユーザーの不興を買った反省を経て、「古い順」という言葉そのものを手がかりに
ソート順マッピングを独立して検証した。

実サーバーへ直接fetchし、cid（カードID。値が大きいほど新しいカード）を比較した結果:

| API値 | 実際の挙動 |
|------|-----------|
| `sort=20` | 最古のカードのみ返る（cidが4000番台） |
| `sort=21` | 最新のカードのみ返る（cidが20000番台） |

`src/api/mappers/card-search-mapper.ts` の `SORT_ORDER_TO_API_VALUE` では
`release_desc`（新しい順のつもり）に20、`release_asc`（古い順のつもり）に21を割り当てていたが、
実際のサーバーの意味は完全に逆だった。

デフォルトソートは `release_desc` のため、この逆転バグにより**常に最古のカードから100件が
取得されていた**。「通常(Normal)」タイプは2004年頃までの最初期のカードにほぼ全て付与される
分類のため、最古カードの集合は通常モンスターに偏る。これが「通常モンスターだけ・古い順」という
症状の直接の原因だった。AND/OR絞り込みとは無関係で、デフォルトソートを使うあらゆる検索に影響する。

### 修正

`release_desc`→21、`release_asc`→20 に修正。既存の
`src/api/__tests__/card-search-mapper.test.ts` が誤った値をハードコードしていたため、
検証結果に合わせて更新した。

---

## 教訓

- ユーザーの短い指摘（「一度ORの状態の検索結果が表示されるままだ」）を軽視せず、原因が
  見つからない場合は「本当にないか」を疑うのではなく、別の角度（この場合は「古い順」という
  副次的な描写）から再検証することで真因にたどり着けた
- クライアント側の後処理（`applyClientSideFilters`）で症状が偶然解消しても、リクエスト自体が
  壊れているという本質的な問題を見逃す可能性がある。ユーザーからの独立した確認を経て
  実サーバーの生レスポンスで検証したことが本当の原因の発見につながった
- APIパラメータの数値の意味は名前から類推せず、実サーバーで直接検証する
